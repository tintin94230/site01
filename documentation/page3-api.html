Page 3 – API internes & base de données

Cette page documente les API backend internes du projet et la structure de la base de données Supabase.

1️⃣ Principe général

Les pages HTML du site n’accèdent jamais directement à la base de données.

Toutes les opérations passent par des API serverless hébergées sur Vercel. 

Navigateur (HTML / JS)
        |
        v
API serverless (/api/*)
        |
        v
Supabase (PostgreSQL)

Ce principe garantit :

  • la protection des clés Supabase
  • la centralisation de la logique métier
  • une séparation claire frontend / backend
  • une architecture évolutive

2️⃣ API /api/supabase001

API utilisée par la page blog.html.

Objectif

API simple et pédagogique servant d’exemple d’interaction entre une page HTML et Supabase.

Fonctions

  • Recevoir un mot depuis le navigateur
  • Calculer la longueur du mot
  • Insérer le mot dans la base

Endpoint

GET /api/supabase001?mot=bonjour

Flux de traitement

blog.html
   |
   | fetch("/api/supabase001?mot=bonjour")
   v
API supabase001
   |
   | INSERT INTO mots
   v
Supabase

Table utilisée : mots

ColonneDescription
idIdentifiant unique
motMot saisi par l’utilisateur
created_atDate d’insertion

👉 Cette API sert principalement de démonstration.

3️⃣ API /api/supabase002

API utilisée par admin.html et admin-lieux.html.

Objectifs

  • Gestion structurée des données
  • Ajout, modification, suppression
  • Logique métier côté serveur

Données manipulées

  • Lieux géographiques
  • Itinéraires entre lieux

Flux typique

admin-lieux.html
      |
      | fetch("/api/supabase002", data)
      v
API supabase002
      |
      | INSERT / UPDATE / SELECT
      v
Supabase

⚠️ Cette API est destinée à être protégée (authentification, rôles, etc.).

4️⃣ Base de données Supabase

La base est hébergée sur Supabase (PostgreSQL managé).

Table : mots

Utilisée par /api/supabase001.

ColonneDescription
idIdentifiant unique
motMot stocké
created_atDate de création

Table : lieux

Représente des lieux géographiques.

ColonneDescription
idIdentifiant unique
nomNom du lieu
latitudeCoordonnée GPS
longitudeCoordonnée GPS
created_atDate de création

Ces données sont gérées via /api/supabase002.

Table : itineraires

Représente un trajet entre deux lieux.

ColonneDescription
idIdentifiant unique
lieu_depart_idRéférence vers lieux.id
lieu_arrivee_idRéférence vers lieux.id
type_voyageVoiture, train, avion…
nomNom de l’itinéraire
descriptionDescription libre
lien_httpLien externe
created_atDate de création

Relations

lieux (id)
   ▲        ▲
   |        |
   |        |
itineraires
(depart) (arrivee)

Les clés étrangères garantissent la cohérence des itinéraires.

5️⃣ Environnements DEV / PROD

Les API utilisent des variables d’environnement : 

SUPABASE_URL
SUPABASE_KEY

Chargées depuis :

  • .env.local en développement
  • Vercel Environment Variables en production

👉 Voir Page 2 – Outils & déploiement

6️⃣ Sécurité

  • ❌ Aucune clé dans le HTML
  • ✅ Accès base uniquement via API
  • ✅ Séparation DEV / PROD
  • ✅ Clés stockées côté serveur

7️⃣ Résumé

  • /api/supabase001 → API simple et pédagogique
  • /api/supabase002 → API structurante (lieux, itinéraires)
  • Supabase fournit une base relationnelle robuste
  • L’architecture est prête pour des évolutions futures
